# nLink 0.7.0 hotfix revision 2

Status: **unreleased candidate**. The app and installer version remain `0.7.0`. The proposed separate release tag is `v0.7.0-hotfix.2`; no tag, CI run or final artifacts have been selected for this revision.

## Scope

- Include the committed wallet unlock/relink race and verifier-cancellation fixes (`8e8f1408`) and the recovery-keyframe test fix (`9237f2d9`).
- An explicit Tuna unlock in an idle approved session with Screen permission uses the same ordinary lane handshake as automatic session startup. It no longer selects File-only preparation for a combined file/screen session or waits for a file-transfer activation transaction in a screen-only session.
- No dummy transfer or screen-share start is needed. A verified, approved session, an explicitly enabled payer and a completed authenticated handshake are still required. The other peer may remain a non-paying dialer.
- File-only preparation, file admission/route publication, active-transfer unlock, fallback/retry authority, replay protection, application deadlines and spending limits remain unchanged. A connected lane is not permission to publish a file route or proof that payload was delivered.

## Validation boundary

Focused fake-transport tests exercise idle negotiation for either paying peer, screen-only and combined permissions, no readiness before the answer, stop/late-answer rejection, and subsequent explicit file admission. Existing preparation and mixed-lane admission/retirement regressions cover the preserved authority boundaries. These are deterministic tests, not live Tuna qualification.

Local results on 16 November 2026: all **8 new idle-session cases passed**; **51 existing preparation and mixed-lane startup cases passed** against the same production change in the preceding focused run. That preceding run also retained four failures in the new tests' log-based stop observation; the final tests deliver the held authenticated answer directly at the handler boundary and assert state instead of depending on a redacted message ID. Earlier setup/compile failures and the initially reproduced screen-only failures are not relabeled as passes. No live application or sidecar was launched for these checks.

The earlier live screen-only logs also contained `replay_stale` answer rejections. This candidate does not bypass or enlarge the replay window and does not claim to repair delayed negotiation during concurrent control/media traffic. The targeted behavior is establishing Tuna while the approved session is still idle.

Before release, retain focused results, review and commit only the intended changes, then obtain required CI results and validate that exact portable/installer. Confirm idle Tuna readiness before starting file transfer or screen sharing on the selected portable, followed by the applicable route and clean-stop checks. Preserve the original scope of all historical results; case 10323 remains paused.
