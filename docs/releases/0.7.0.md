# nLink 0.7.0

`0.7.0` keeps the H.264 screen-sharing path and normal NKN transport defaults from `0.6.2`, keeps regular file transfer on V4, routes active file Tuna over V4, and reserves V6 file transfer for one-shot controlled post-Tuna fallback or explicit unsafe diagnostics. This release adds experimental NKN Tuna readiness work and a visible Options wallet-linking UX. Tuna is not enabled automatically and does not replace nLink's application-level session security.

## Highlights

- Options includes a `Wallet` tab with a `Tuna (experimental)` wallet-linking section.
- Users can link a local `wallet.json`, validate balance with a session-only password prompt, copy the public wallet address, and unlink the wallet.
- Wallet linking stores only local state and public validation metadata; it never copies the wallet file and never persists the password, seed, private key, or decrypted wallet material.
- `nlink-tuna-sidecar` includes a safe `wallet-status` mode that validates a wallet and exits without starting a paid listener, dialing Tuna, or spending NKN.
- Tuna acceleration remains default-off and requires explicit advanced opt-in.
- Tuna capability exchange is bound to the approved, verified nLink session and silently falls back to the current NKN transport on mismatch or sidecar failure.
- The session header Tuna pictogram is gray when inactive, light blue for the non-paying dialing side, and yellow on the computer selected as the paid Tuna listener.
- Payer selection is helpee-priority when both sides are unlocked; stale payer offers/answers are rejected so a late helper or helpee attempt cannot flip the active Tuna state.
- Helper-paid Tuna startup uses a short adaptive grace wait for helpee intent instead of always waiting the full payer-priority window.
- The experimental runtime pilot now requires full Tuna provider readiness before advertising Tuna as usable; degraded 3-path readiness is limited to explicit diagnostic A/B runs with `NLINK_NKN_TUNA_ALLOW_DEGRADED_PROVIDER_READY=1`.
- Phase 3 benchmark tooling compares current NKN and Tuna using file, screen, and reconnect profiles.
- Route acceptance validates regular NKN V4, active Tuna V4, and controlled post-Tuna V6 fallback before installer creation. Tuna remains experimental/default-off because provider path degradation and retry caveats are still monitored.

## File transfer and session security

- File transfer is route-aware and single-file only.
- Regular NKN uses `regular_nkn_v4_fast`, protocol `4`.
- Active file Tuna uses `file_tuna_v4`, protocol `4`.
- Live post-Tuna fallback uses one-shot `post_tuna_fallback_v6`, protocol `6`, for the affected transfer; after final fallback completion succeeds, the next new file transfer resolves from current transport state.
- Diagnostic regular-NKN V6 uses `diagnostic_regular_nkn_v6` and is unsafe opt-in only.
- Inbound file transfer still requires explicit accept/decline.
- Active file transfers can be paused, resumed, or canceled from either side when file transfer is allowed for the session.
- File-transfer lifecycle actions are hard-priority: cancel, pause, session end, peer down, window close, and app exit bypass file-data queues, repair queues, Tuna, and bulk backlog.
- When Tuna stops during active Tuna V4, the same transfer live-transitions to `post_tuna_fallback_v6` over regular NKN. If Tuna comes back before terminal completion, the same transfer can return to `file_tuna_v4`; final fallback completion consumes fallback state before the next transfer.
- File-transfer data is protected by nLink's session envelope and source/session validation; this release does not treat NKN transport alone or Tuna transport encryption as the security boundary.
- Existing file-transfer limits remain in place, including the `25 GiB` default file-size cap, `512` frame / `32 MiB` inbound data-session queue, and `64 KiB` bridge binary payload cap before allocation.

## Tuna experimental limits

- Tuna is not enabled unless explicitly enabled through the advanced opt-in path or developer runtime flags.
- Linking or validating a funded wallet does not start a Tuna listener, dial a peer, spend NKN, or change the default transport.
- The packaged Tuna sidecar is present so Options can run one-shot wallet validation, but this does not promote Tuna acceleration to default runtime behavior.
- Runtime acceleration remains limited to eligible screen media frames and file-transfer data frames after the normal nLink approval and verified session handshake.
- Chat, consent, handshake, remote control, screen control, and file-transfer control messages remain on the current NKN bridge.
- Automatic "funded wallet means prefer Tuna" behavior is still deferred.

## Screen sharing, chat, and shell UX

- H.264 screen sharing remains the default path.
- Options -> Settings exposes Balanced, High quality (`24` capture FPS / `15` transport FPS / `1440x810` max), Tuna quality, and High performance screen-share presets.
- Chat input remains usable while screen sharing, including `Enter` to send and `Shift+Enter` for a new line.
- Normal release UX continues to use explicit helpee consent and session verification before allowing a session.

## Limits

- Windows x64 only.
- Single-file transfer only.
- Inbound transfer requires explicit accept/decline.
- File-transfer pause/resume applies to the active in-session transfer and does not resume after app restart.
- Large file-transfer throughput and live screen-share delay can still depend on NKN/network delivery variance.
- Tuna remains experimental and default-off.

## Support notes

For connection or approval issues, start with **Options -> Diagnostics -> Copy diagnostics** from both sides when possible. Diagnostics export redacts Tuna wallet paths, wallet addresses, passwords, seeds, and private-key material from copied/exported support text.
