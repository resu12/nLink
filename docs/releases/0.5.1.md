# nLink 0.5.1

`0.5.1` is the stabilization and hardening release after `0.5.0`, which introduced the first native nLink file-transfer flow. This release keeps that native in-session transfer model, then hardens the session shell, transport path, and release-default security posture around it.

## Important updates since 0.5.0

- Chat now uses the same session-secure envelope path as the other sensitive session traffic.
- Protected NKN seed storage is now the intended release path across supported desktop platforms; plaintext seed fallback is no longer part of the normal model.
- Diagnostics now explicitly say redaction is best-effort and include persistence/storage failure visibility.
- Privileged runtime actions now execute through a stricter internal authorization boundary.
- The local bridge hot path no longer uses JSON `payloadBase64` for large send/receive traffic; hot payload traffic now uses a framed binary stdio protocol.
- File transfer was reworked substantially for transport-aware reconnect behavior, bulk-path handling, and post-`0.5.0` reliability stabilization.

## Highlights

- Native in-session file transfer remains part of the active authenticated session.
- Screen sharing, remote control, chat, and transfer remain inside the same privacy-first approval model.
- `Transfer files` remains a dedicated capability in the session approval model.
- Release packaging, diagnostics, and bundled bridge artifacts now consistently identify the build as `0.5.1`.

## Security and Privacy

- Chat is now protected on the same session-cryptographic transport path as the rest of the sensitive session traffic.
- Helper-bound issued-secret invites and verified-helper public invite flow remain the default release path.
- Diagnostics export now labels redaction as best-effort rather than implying a guaranteed-clean export.
- Persistence problems such as protected secret-store failures are now surfaced in diagnostics instead of failing silently.

## File Transfer and Session Behavior

- Either side can click `Send file` once the active session grants `Transfer files`.
- Transfers are still single-file only in `0.5.1`.
- Progress, cancel, and terminal success/failure state remain visible inside the shared session/chat panel.
- File contents remain protected end-to-end and verified before the transfer is marked complete.
- File transfer remains bound to the active authenticated session and peer identity.
- The transfer path now includes transport-aware pause/resume handling and updated NKN bulk-path behavior after the first `0.5.0` release.

## Storage and Safety

- Received files are assembled through a temp-first flow and finalized only after byte-count and whole-file SHA-256 verification succeed.
- Received files are not auto-opened.
- Save behavior is safe by default and does not silently overwrite an existing file.
- The receiver writes into an app-owned folder under `%LOCALAPPDATA%\nLink\transfers\incoming\...`.
- `0.5.1` enforces a single-file size cap of `256 MiB`.

## Current Limits

- Single-file transfer only
- No folder transfer
- No drag-and-drop
- No resume after restart
- No transfer queue
- Large file transfers over NKN can still be noticeably slower than direct local-network copy

## Notes

- Invite-based connect remains the primary flow:
  - helper shares a helper address
  - helpee enters that helper address and confirms the verification code
  - helpee shares the invite with QR, share, and copy actions
  - helper connects by pasting an invite code or scanning a QR code
- Release diagnostics should report:
  - `invite_security_mode: issued_one_time_secret_invites`
  - `invite_public_flow: verified_helper_required`
  - `invite_security_release_ready: Yes`
  - `invite_security_warning: none`
- Current release assets live under `artifacts/releases/0.5.1/`.
