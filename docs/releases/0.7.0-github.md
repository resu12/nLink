# nLink 0.7.0

`0.7.0` keeps the current NKN transport and H.264 screen-sharing path, keeps regular file transfer on V4, routes active file Tuna over V4, and reserves V6 file transfer for one-shot controlled post-Tuna fallback or explicit unsafe diagnostics.

## Highlights

- New `Tuna (experimental)` section in Options -> Wallet.
- Link a local `wallet.json`, validate balance with a session-only password prompt, copy the public wallet address, and unlink the wallet.
- Wallet validation never copies the wallet, persists the password, starts a paid listener, dials Tuna, or spends NKN.
- Safe sidecar `wallet-status` mode validates a wallet and exits.
- The Tuna sidecar verifier is bundled for packaged Options wallet validation.
- Tuna remains default-off and requires explicit advanced opt-in; a linked or funded wallet does not change runtime transport behavior by itself.
- Tuna negotiation is bound to the approved, verified nLink session and falls back to the current NKN bridge on mismatches or sidecar failure.
- The session header Tuna pictogram is gray when inactive, light blue for the non-paying dialing side, and yellow on the computer selected as the paid Tuna listener.
- Payer selection is helpee-priority when both sides are unlocked; stale payer offers/answers are rejected so a late helper or helpee attempt cannot flip the active Tuna state.
- Helper-paid Tuna startup uses a short adaptive grace wait for helpee intent instead of always waiting the full payer-priority window.
- The experimental runtime pilot now requires full Tuna provider readiness before advertising Tuna as usable; degraded 3-path readiness is limited to explicit diagnostic A/B runs with `NLINK_NKN_TUNA_ALLOW_DEGRADED_PROVIDER_READY=1`.
- Phase 3 benchmark tooling compares current NKN and Tuna for file, screen, and reconnect profiles.
- Route acceptance validates regular NKN V4, active Tuna V4, and controlled post-Tuna V6 fallback before installer creation, while Tuna remains experimental/default-off because provider path degradation and retry caveats are still monitored.

## Security and transport notes

- Route-aware single-file transfer with explicit accept/decline before receive.
- Regular NKN uses `regular_nkn_v4_fast` / protocol `4`; active file Tuna uses `file_tuna_v4` / protocol `4`; controlled post-Tuna fallback uses a fresh one-shot `post_tuna_fallback_v6` / protocol `6`, then a successful fallback returns the next new file transfer to regular V4.
- File-transfer lifecycle actions are hard-priority, so cancel, pause, session end, peer down, window close, and app exit bypass file-data queues, repair queues, Tuna, and bulk backlog.
- Active Tuna V4 is not mutated in place to V6 when Tuna stops; the live transfer stays V4 and recovers over regular NKN. Controlled fallback starts a fresh one-shot V6 measured transfer and must prove route/protocol/runtime consistency before it is accepted.
- File-transfer data remains protected by nLink's session envelope and source/session validation.
- nLink does not rely on NKN transport alone or Tuna transport encryption as the application security boundary.
- Chat, consent, handshake, remote control, screen control, and file-transfer control messages stay on the current NKN bridge.
- Diagnostics redaction covers Tuna wallet paths, wallet addresses, password-like fields, seeds, and private-key material.

## Limits in 0.7.0

- Windows x64 only.
- Single-file transfer only.
- Inbound transfer requires explicit accept/decline.
- `25 GiB` default file-size cap.
- Pause/resume applies to the active in-session transfer and does not resume after app restart.
- Tuna is experimental, default-off, and not automatically promoted by linking or funding a wallet.
- Large file-transfer throughput and live screen-share delay can still depend on NKN/network delivery variance.
