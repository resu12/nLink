# Frontier obligations across route supersession

## Status and scope

This is a bounded disposition proposal and test contract, not an acceptance-policy
change. Existing classifications, raw/distinct/recovered/unresolved counts, and
completed-proof gates remain unchanged. In particular, historical helper 11350
remains unresolved with `SourceSuperseded` diagnostic metadata and quartet
`1/1/0/1`. That archived result is not a claim about the later bootstrap-ownership
report and has not been replayed for this review.

Reviewed against `8577cbd017d143b362009df4393429f97fb2df7d` on 2026-09-12.
The implementation status below supersedes the earlier first-install-only gap
description; it does not approve the proposed classification/count policy.

The proposal separates four subjects which must not be collapsed into one
"recovery" result:

| Subject | Sufficient evidence | What it does not prove |
|---|---|---|
| Scheduled wake | Exact current wake, grant, delivery, dispatch and send | Successful repair or frontier progress |
| Repair attempt A | Its exact immutable terminal settlement | Transfer of A's outcome to a successor |
| Old source scope | Exact committed route replacement, current-owner retirement, applied disposition and publication with preserved durable checkpoint/data session | Cancellation or successful settlement of historical A |
| Target route | Its own current Coordinator authority, peer-bound preparation/admission, checkpoint adoption and publication | Permission to accept old-source requests or borrow later progress for A |

A request that was dispatched and then settled `SettledStalled` is not a missing
wake. It is also not a successful repair. An exact successor B may later be
retired by route replacement without changing A's settlement.

## Proposed disposition, pending approval

Recommend a distinct, neutral **superseded-source disposition** for the analyzer's
source-bound progress obligation, once exact source retirement and target
checkpoint ownership are established. It would not be `Recovered`, would not
erase the stalled attempt, and would not waive unrelated transfer, route,
evidence or finalization failures. No existing receipt is reinterpreted as a
Coordinator cancellation of A: the longer-lived obligation is analyzer policy,
not a separately issued runtime entity.

The current `SourceSuperseded` diagnostic alone is insufficient to activate this
proposal. Joined peer evidence and an explicit decision about classification and
count accounting are prerequisites. Until that decision, the obligation stays
unresolved. Do not move it into the recovered count, silently omit it from the
distinct count, or manufacture a passing quartet.

## Joined contract fixture

The following is required positive proof, not a claim that the existing fixtures
already establish it. The queued first-install test bridge now forwards the
actual paired-release request through service authorization, staging, receipt
issuance, install confirmation and exact paired-release consumption. Only the
sender installs; the receiver remains on its paired fallback source. An exact
duplicate queue request does not dispatch twice or consume the release again.

The negative confirmation path exposed a separate stale-state rollback defect.
The approved fix now compensates from the exact current Coordinator state in
both directions, preserves consumed release history and the exact predecessor,
and clears only the failed transport proposal. Focused runtime and
family-specific evidence tests pass; no historical obligation is marked
recovered. See [the bounded RCA and results](file-transfer-retry-confirmation-rollback-rca.md).
The complete joined route-overlap positive combining the A/B repair lineage,
old-source request/replay rejection and target handoff remains unproven.

Use one transfer and connected real test data-session queues. Starting fallback
contexts may be controlled fixture inputs; completed route transitions, paired
releases and repair settlements must be generated by the Coordinator/service
paths being tested.

1. Exchange the two actual Coordinator-issued yield proofs and validate their
   exact peer/pair lineage. Writer-local Coordinator generations remain distinct.
2. Generate the sender's PostFallback-to-Tuna preparation, drain, commit,
   publication and disposition. A seeded committed sender is not this proof.
3. Let the receiver's unchanged wake and rescue cadence dispatch A, settle A
   stalled and install B. Deliver the receiver's actual emitted old-fallback
   request through the sender's live receive queue, including one exact replay.
4. Require both requests to be stale-rejected without a sender repair grant,
   route mutation or progress. Rejection is correct behavior, not target failure.
5. Complete the receiver's exact handoff. Its current B may retire; A must remain
   stalled. Both target owners must preserve the durable frontier and their
   respective data-session identities.
6. Any subsequent target-route repair/progress must belong to its own current
   authority and publication. It cannot retrospectively recover A.

## Negative evidence and consumer selection

Missing, foreign or ambiguous commit/disposition/publication, wrong peer binding,
data-session replacement, pause/terminal poison, conflicting duplicates and
A-to-B-to-A restoration must not establish supersession or target ownership.
Rejected admission cannot supply positive authority; a state-neutral rejected
callback does not by itself invalidate already-established current ownership.
Byte-identical duplicates may coalesce only under the existing rules.

Full, independently regenerated compact and shared GUI consumers must select
the same exact candidate metadata. A later `SourceSuperseded` diagnostic cannot
be attached to an earlier unresolved candidate that has no diagnostic. Absent
and null optional metadata must remain absent/null through normal classification
and formatting; they cannot become a recovered verdict.
